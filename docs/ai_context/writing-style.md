# Writing style — replies, PRs, commits, HENGE prose

**Copied into this repo 2026-09-11** from the author's canonical copy, which lives elsewhere; edit it there and re-copy. Applies to everything written here for a human: the README, work pages, commit messages, PR descriptions, HENGE prose.

Applies to anything written for a human to read: chat replies, PR descriptions, commit messages, HENGE prose, code comments. Does not apply to code syntax itself.

## The rules

1. No em dashes. Use a regular dash, colon, comma, full stop or a conjunction. Don't substitute a semicolon or an ellipsis everywhere either, the fix is usually two sentences.
2. The answer or the recommendation goes in the first sentence, plainly. Reasoning follows as its own sentences.
3. Full sentences. No fragment chains, and `X → Y` is not a claim.
4. No label announcing what you are about to write: "in plain terms:", "to summarise:", "the key point is:", "here's what I found:".
5. No opener or closer that carries no content: "Great question", "You're absolutely right", "Perfect!", "Let me be direct", "Hope that helps", "Let me know if you'd like me to dig deeper".
6. No artificial contrastive negation and no rule-of-three padding. Do not tell the reader
   what something is not before saying what it is, and do not stack absolute negations
   (never, none, not, no) to manufacture tension or a mic-drop tone. Avoid: "This is not a
   tool. It is a paradigm shift." Avoid: "No fluff. No filler. None of the usual excuses.
   Just results." Avoid: "Success was never about the destination. It was about the
   journey." Write directly and affirmatively: state the fact, the description or the
   value plainly, without a fake contrast or a dramatic binary to sound deep. Better: "This
   tool changes how teams collaborate." Better: "We deliver direct results without the
   usual filler." (Expanded here 2026-09-12, ahead of the canonical copy; carry it back.)
7. No inflated words: robust, seamless, comprehensive, crucial, leverage, ensure, delve, "deep dive". Use a plain verb or the specific fact.
8. Say it once. Don't restate the claim in simpler words in the next sentence.
9. Say "I don't know" or "I haven't checked" in those words. Never claim a result you haven't seen: name the command and what it printed.
10. Bullets only for parallel items. No emoji or status glyphs. Bold once per long block at most.
11. Don't pad. A one-sentence answer is one sentence.
12. Vary paragraph length. Every paragraph running to three sentences is the strongest tell there is.
